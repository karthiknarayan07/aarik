# ADR 0001: Dolby Vision downscale route

Status: **Proposed — gate pending owner clips**

## Context

Spec section 8.3a makes Dolby Vision preservation a release gate: resizing a 4K iPhone clip to 1080p must keep
genuine Dolby Vision (profile 8.4, an RPU on every frame) and the iPhone metadata. If it does not, v1 does not ship,
and we do not paper over it with a plain HDR fallback.

## Candidate route A: VideoToolbox HDR metadata insertion

Re-encode with `VTCompressionSession` (HEVC) and set:

- `kVTCompressionPropertyKey_HDRMetadataInsertionMode` = `kVTHDRMetadataInsertionMode_Auto`, with dynamic HDR
  metadata preserved, for Dolby Vision sources.
- `kVTHDRMetadataInsertionMode_None` for non-DV sources.
- 8-bit sources stay HEVC Main 8-bit; 10-bit sources, and sources whose bit depth can't be read, use Main10.
- Static HDR metadata from the source format description: `kVTCompressionPropertyKey_MasteringDisplayColorVolume`
  and `kVTCompressionPropertyKey_ContentLightLevelInfo`. Ambient viewing environment has no VideoToolbox session
  property, so it is attached to every frame (`kCVImageBufferAmbientViewingEnvironmentKey`).

## Evidence so far (synthetic only)

All synthetic evidence below was taken on macOS 27.2 (Apple Silicon). The Dolby Vision auto-insertion is macOS 27.2
encoder behavior; an earlier or later macOS may not add it, which would change every synthetic result here.

- On macOS 27.2 the HEVC Main10 HLG encoder auto-inserts a `dvvC` record (DV profile 8, compat 4; the level tracks
  the resolution).
- Synthetic 4K60 and 4K30 HLG fixtures (DV 8/7/4) downscaled to 1080p give output DV profile 8, level 4, compat 4.
  Metadata diff: changed = {`video.dimensions`, `hdr.dolbyVision`}, lost = none.
- `scripts/dv-check.sh`:
  - 1080p synthetic output: 30/30 frames carry an RPU (config 8/4/4).
  - 90 s 4K HLG fixture downscaled: 2700/2700 frames carry an RPU.
  - SDR output: 0 RPU, and the script fails as expected.
  - Truncated file: the script fails.
- `scripts/dv-compare.sh` on the synthetic 4K30 HLG fixture against its 1080p output (30 frames, ffprobe 8.1.1):
  identical reshaping curves on 30/30 frames, identical other RPU fields on 30/30 frames, max |Δ source_min_pq| = 0,
  max |Δ source_max_pq| = 0, scene refresh on 30/30 frames in both; L1/L2/L5 not printed by ffprobe;
  verdict INCONCLUSIVE (exit 3). See "Preserved vs regenerated RPU" below.
- Caveat: route A's properties behaved the same as the encoder default on synthetic input. Whether a real iPhone
  RPU is carried through (rather than regenerated by the encoder) is **unproven** until real clips are run.

## Preserved vs regenerated RPU

`dv-check.sh` only shows that every output frame has *an* RPU. Route A may hand the source RPU through, or the
encoder may re-analyse the downscaled frames and write a new one. A regenerated RPU can still look right, but it
replaces the camera's own per-shot analysis and any trims.

`scripts/dv-compare.sh <source> <output>` compares the two per frame, aligned by frame index (the frame counts
must match):

- L1 (min/avg/max PQ per frame): max |Δ| per field, against a tolerance of 41 PQ codes (1% of the 12-bit range,
  `L1_TOLERANCE` at the top of the script).
- L2 (trims): whether present in source and output.
- L5 (active-area offsets): output frames with non-zero offsets (a 16:9 iPhone frame has none).
- Always, from what ffprobe prints: max |Δ| of `source_min_pq` / `source_max_pq`, frames with identical reshaping
  curves (pivots, polynomial and MMR coefficients), frames with identical other RPU fields, scene-refresh counts.

Exit 0 (PASS) needs every frame's L1 within tolerance, matching L2 presence and zero output L5 offsets. Exit 1 is
FAIL. **ffprobe 8.1.1 (this machine) does not print the L1/L2/L5 extension blocks** (its Dolby Vision output stops
at `source_diagonal`), so the script ends INCONCLUSIVE (exit 3) and only the "always" lines are measured. Reading
L1/L2/L5 needs a tool that parses RPU extension blocks (for example `dovi_tool`, MIT), which was not installed for
this plan.

Synthetic result (above): every field ffprobe prints is identical frame for frame. That fits a preserved RPU, but
on synthetic HLG input the encoder's auto-inserted RPU is the same for any content, so it cannot tell the two apart.
Only real clips can.

**Owner decision required:** Is a regenerated (re-analysed) RPU acceptable if L1 stays within tolerance and L2
trims are kept?

## Gate procedure

Preconditions: clips in `Fixtures/iphone/` (see `Fixtures/README.md`).

PASS requires all of:

1. `AARIK_GATE=1 swift test --filter RealClipGateTests` is green, so no clip is skipped (DV clips are 4K and come
   out 1920x1080 with DV profile 8 / compat 4 kept and only the level changed; nothing lost; nothing else changed
   beyond the dimensions; iPhone `qt.` metadata, including the location, identical; spatial audio tracks, their
   enabled state, groups and fallbacks identical; slo-mo frame rate kept; Live Photo identifier kept; SDR stays
   SDR; spatial video refused).
2. `scripts/dv-check.sh <output>` exits 0 on each DV output (RPU on every frame).
3. `scripts/dv-compare.sh <source> <output>` on each DV source/output pair does not FAIL, and its output is
   recorded here. PASS (exit 0) meets this. INCONCLUSIVE (exit 3, what ffprobe 8.1 gives) meets it only once the
   owner decision above is answered and recorded, since L1/L2/L5 were not measured.
4. The owner confirms in QuickTime Player and Photos that each DV output shows as Dolby Vision / HDR and looks like
   the source.

On PASS: accept route A, and record the observed kept/lost lists per clip type here. They become spec section
8.3's confirmed expected-loss list.

On FAIL of any DV check, before stopping:

1. Export the same clip with `AVAssetExportSession` and `AVAssetExportPresetHEVC1920x1080`, then run
   `dv-check.sh` on it. This shows whether Apple's own export keeps DV, and so whether route A's settings or the
   route itself is wrong.
2. Record route A as rejected, with the evidence.
3. Stop. Plan 2 does not start. The next plan becomes route C (spec section 8.3a): extract the RPU from the
   source, adjust the L5 active-area metadata for the new frame, and re-inject it into the encoded stream.

## Open questions to confirm with real clips

- Mastering display, content light level and ambient viewing environment are now inventoried
  (`hdr.masteringDisplay`, `hdr.contentLightLevel`, `hdr.ambientViewingEnvironment`) and carried as described
  under route A; synthetic clips carrying all three keep them. On real iPhone clips they may not be carried (for
  example if the encoder rejects a value); the report then lists them as lost. Confirm with real clips.
- Resolution-dependent pixel-buffer attachments (for example clean aperture) may need to be rewritten for the
  new size.
- Reader edit lists and AAC priming on real iPhone files (synthetic files have neither) may affect timing and
  audio start.
