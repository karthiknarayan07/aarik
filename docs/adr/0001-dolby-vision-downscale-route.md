# ADR 0001: Dolby Vision downscale route

Status: **Proposed — gate pending owner clips**

## Context

Spec section 8.3a makes Dolby Vision preservation a release gate: resizing a 4K iPhone clip to 1080p must keep
genuine Dolby Vision (profile 8.4, an RPU on every frame) and the iPhone metadata. If it does not, v1 does not ship,
and we do not paper over it with a plain HDR fallback.

## Candidate route A: VideoToolbox HDR metadata insertion

Re-encode with `VTCompressionSession` (HEVC) and set:

- `kVTCompressionPropertyKey_HDRMetadataInsertionMode` = `kVTHDRMetadataInsertionMode_Auto`, with dynamic HDR
  metadata preserved, for Dolby Vision sources.
- `kVTHDRMetadataInsertionMode_None` for non-DV sources.
- 8-bit sources stay HEVC Main 8-bit; 10-bit sources use Main10.

## Evidence so far (synthetic only)

- On macOS 27.2 the HEVC Main10 HLG encoder auto-inserts a `dvvC` record (DV profile 8, compat 4; the level tracks
  the resolution).
- Synthetic 4K60 and 4K30 HLG fixtures (DV 8/7/4) downscaled to 1080p give output DV profile 8, level 4, compat 4.
  Metadata diff: changed = {`video.dimensions`, `hdr.dolbyVision`}, lost = none.
- `scripts/dv-check.sh`:
  - 1080p synthetic output: 30/30 frames carry an RPU (config 8/4/4).
  - 90 s 4K HLG fixture downscaled: 2700/2700 frames carry an RPU.
  - SDR output: 0 RPU, and the script fails as expected.
  - Truncated file: the script fails.
- Caveat: route A's properties behaved the same as the encoder default on synthetic input. Whether a real iPhone
  RPU is carried through (rather than regenerated by the encoder) is **unproven** until real clips are run.

## Gate procedure

Preconditions: clips in `Fixtures/iphone/` (see `Fixtures/README.md`).

PASS requires all of:

1. `swift test --filter RealClipGateTests` is green (DV profile 8 / compat 4 kept, nothing lost, iPhone `qt.`
   metadata identical, spatial audio identical, slo-mo frame rate kept, Live Photo identifier kept, SDR stays SDR,
   spatial video refused).
2. `scripts/dv-check.sh <output>` exits 0 on each DV output (RPU on every frame).
3. The owner confirms in QuickTime Player and Photos that each DV output shows as Dolby Vision / HDR and looks like
   the source.

On PASS: accept route A, and record the observed kept/lost lists per clip type here. They become spec section
8.3's confirmed expected-loss list.

On FAIL of any DV check, before stopping:

1. Export the same clip with `AVAssetExportSession` and `AVAssetExportPresetHEVC1920x1080`, then run
   `dv-check.sh` on it. This shows whether Apple's own export keeps DV, and so whether route A's settings or the
   route itself is wrong.
2. Record route A as rejected, with the evidence.
3. Stop. Plan 2 does not start. The next plan becomes route C (spec section 8.3a): extract the RPU from the
   source, adjust the L5 active-area metadata for the new frame, and re-inject it into the encoded stream.

## Open questions to confirm with real clips

- Mastering display, content light level, and ambient viewing environment metadata are not yet carried through
  by route A, nor are they inventoried by `MediaInspector`.
- Resolution-dependent pixel-buffer attachments (for example clean aperture) may need to be rewritten for the
  new size.
- Reader edit lists and AAC priming on real iPhone files (synthetic files have neither) may affect timing and
  audio start.

## Decision

Pending. The gate has not been run on real clips.
