# Plan 5 — Release Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship v0.1.0 as an ad-hoc-signed DMG on GitHub Releases. In-app updates come through Sparkle 2, with appcasts signed using EdDSA. CI runs on every PR, and the README and docs are ready for first users.

**Architecture:**

- Sparkle 2 is added to the app target only (spec §12: the sole runtime dependency) as a Swift Package dependency of `App.xcodeproj`. The engine packages stay dependency-free.
- `SPUStandardUpdaterController` lives in `AppDelegate`.
- Settings gains "Check for updates automatically" and "Check now".
- The feed URL and the public EdDSA key are set in `Config/App.xcconfig` → Info.plist (`SUFeedURL`, `SUPublicEDKey`). The brand stays in `Brand.xcconfig`.
- The release workflow builds the DMG (existing `scripts/make-dmg.sh`), signs it with Sparkle's `sign_update` using the private key from a GitHub secret, updates `appcast.xml` on the `gh-pages` branch, and uploads the DMG to the Release.

**Already done (Plan 2 groundwork):**

- `.github/workflows/ci.yml`
- `.github/workflows/release.yml` (with a `TODO(sparkle)`)
- `scripts/make-dmg.sh`
- `README.md`

## Global Constraints

- **Brand-neutral code.** The feed URL is derived from `APP_BUNDLE_ID_PREFIX` / repo slug variables in xcconfig, never hard-coded in Swift.
- **No network use except Sparkle's update check.** The check is opt-out in Settings and off when the feed URL is empty, as in dev builds.
- **Secret handling:**
  - The EdDSA private key is generated by the **owner** (`generate_keys`) and stored only in the GitHub secret `SPARKLE_ED_PRIVATE_KEY`.
  - It is never committed and never printed in logs.
  - Only the public key goes into xcconfig.
- **Versioning:**
  - `MARKETING_VERSION` / `CURRENT_PROJECT_VERSION` come from `Config/App.xcconfig`.
  - Tags are `vX.Y.Z` and must match `MARKETING_VERSION`; the workflow fails otherwise.
  - The build number increases monotonically: the workflow uses `github.run_number`.

## Review Focus

1. **Release run without the Sparkle secret:** the workflow fails clearly before publishing anything.
2. **Tag and version mismatch:** the workflow fails before building.
3. **Fresh install from the DMG on macOS 26:** the first-launch "Open Anyway" steps in the README work, and the app runs from /Applications.
4. **Update from v0.1.0 to v0.1.1 via Sparkle with an ad-hoc signature:** the update installs. Sparkle requires EdDSA when there is no Developer ID, and works with ad-hoc signatures.
5. **CI on a PR from a fork:** no secrets are needed; build, test and lint run.

### Task 1: Sparkle in the app

- Add the SPM package `https://github.com/sparkle-project/Sparkle` pinned to the latest 2.x release, current as of the task date (check GitHub releases; pin the exact version).
- Updater controller in `AppDelegate`.
- "Check for Updates…" menu item in the app menu.
- Settings rows: automatic checks on/off (default on) and Check now.
- Info.plist keys via xcconfig:
  - `SUFeedURL = $(APP_UPDATE_FEED_URL)` (empty in Debug)
  - `SUPublicEDKey = $(APP_UPDATE_PUBLIC_KEY)`
  - `SUEnableInstallerLauncherService = NO`, since the app isn't sandboxed

### Task 2: Release workflow — signing and the appcast

Extend `release.yml`:

1. Verify the tag matches `MARKETING_VERSION`.
2. Build the DMG.
3. Download Sparkle's tools (pinned version) and run `sign_update` with the key from the secret, using a masked env and a temp file deleted with `trap`.
4. Generate or append an `appcast.xml` item: version, short version, length, EdDSA signature, release notes from the tag annotation, `minimumSystemVersion` 26.0.
5. Commit it to `gh-pages`.
6. Upload the DMG.

Add the owner steps to `docs/RELEASING.md`:

- generate keys
- add the secret
- set `APP_UPDATE_PUBLIC_KEY` and `APP_UPDATE_FEED_URL`
- enable GitHub Pages
- tag

### Task 2b: UI smoke tests (XCUITest)

Owner's stack calls for XCUITest. Add an `AppUITests` target to `App.xcodeproj` that runs in CI:

- The app gets a launch argument (`-uiTesting`) that points the library and job store at a temporary directory
  and seeds it with generated clips from `MediaTestSupport`; it never reads the real library or Photos.
- Tests:
  - launch shows the Overview welcome
  - add files → grid shows them
  - Quality filter narrows the grid and shows Clear
  - ⌘A selects all and the footer counts follow
  - Add to queue → the job lands in Completed as Verified
  - Settings opens and shows Updates
- Accessibility identifiers only where labels aren't unique.
